# Design system contract

This file is for both audiences. Humans review cards in the terminal with `bun run ds:show`; agents use the contract to change code without inventing a second visual language.

## The rule that keeps it honest

Every card renders the **real** components:

- base pi components come from the pi install resolved at build time;
- ours comes from `packages/pi-ui/render/*`, the exact module the extension ships.
- fold layouts are planned by `packages/pi-ui/extensions/fold.ts`, the module the live session uses, with distances from `blockDistances` in `render/layout.ts`.

A card is therefore a fixture, not an illustration. If the implementation changes, `bun run ds` changes the card's fixture. If a card looks wrong, the product looks wrong.

## Adding a component

1. Pick the semantic token first. Use pi's theme tokens (`accent`, `muted`, `dim`, `success`, `error`, `warning`, `toolTitle`, `toolOutput`, `thinkingText`, …). Never hardcode a hex value.
2. Put the pure renderer in `packages/pi-ui/render/`. It takes data + a render context (`theme`, `width`, `detail`, `expanded`) and returns a `Component` (or lines). No I/O, no timers, no global state.
3. Register it in `design-system/registry.ts`: id, title, group, description, and one render function per state (`pending`, `running`, `success`, `error`, `partial`, `expanded`, `aged0`…`aged6`).
4. Render it. `bun run ds:show <id> --width 40` (and 80, 120), dark and `--theme light`.
5. Add a fixture. The build writes `design-system/fixtures/frames.json`, keyed `<state>/<theme>/<width>/<glyph>`; commit it. `bun run ds:check` fails when the goldens no longer match what the renderers produce.
6. If the component participates in a story, add it to a scenario in `design-system/registry.ts`.

## States every block must survive

| State | Meaning |
|---|---|
| `pending` | called, not started |
| `running` | partial result, animated |
| `success` | completed, no error |
| `error` | failed; must stay legible at every detail level |
| `partial` | streaming arguments or output |
| `expanded` | user pinned it open |
| `aged0..6` | detail level, set by the distance from the tail; 0 is live |

## Detail model

```
distance 0–1    L0      8 body rows plus the header; the live block streams here
distance 2–3    L1      7 rows
distance 4–7    L2–L3   one fewer row at each step
distance 8–9    L4      4 rows (3 content lines plus the omission notice when truncated)
distance ≥ 10   folded into a group: one row per member while the newest
                group of the run has at most 5 rows, then one summary row
```

A block's distance is the number of newer blocks in its run. A step, one level, takes two of them, so a preview keeps one line fewer every two newer blocks. The tail budget (8 above), the blocks per step (2), the fold distance (10, five steps) and the forming size (5 rows) are constants in `render/detail.ts`; nothing in the product changes them.

Rules:

- Completed previews age as newer blocks arrive, including on screen. Visible previews step down one level at a time. A newer block that leaves a preview at its level changes nothing on screen: no fade, no wait. Each departing line fades in place, except in a backlog (below), where rows leave without fading. A departing row fades over a quarter of the recent gap between new blocks in the run (blocks as the fold planner counts them, so a message that only carries tool calls is not one, and blocks arriving within one 20 ms frame of each other count once), between 80 and 480 ms, and over 360 ms until that pace is known, so a fast model's transcript settles quickly and a slow one's steps are easy to follow. A block folds from bottom to top, one row at a time, ending with its heading. A block joining a group that lists its members (a forming group the user has not closed, or a group the user opened) folds only its body and keeps its heading, which becomes its member row.
- The newest group of the current run forms: under its summary it lists one row per member (a tool is one row, a thought one per run) while it has at most five rows, and collapses to the summary at the sixth. A group stops forming when a newer group starts or a user message follows it, so at most one forming group is on screen. Forming follows the member count directly, without hysteresis. When a visible forming group stops forming, its member rows leave from the bottom, each over one fade like any departing row, until only the summary is left; a block whose arrival makes the sixth row first folds through its heading. New blocks arriving mid-collapse, a change to the collapsing group (a member's timing or tokens update, or a member joins or leaves), or a second collapse waiting its turn let the fading row finish; the rest leave one at a time at the backlog's pace. A collapse that a user message starts, or that starts during a backlog, is part of the backlog from its first row. A forming group that merges with a closed one lets its listed rows leave the same way. An offscreen group collapses at once.
- With the default budget, a long preview keeps at least three content lines until it joins its group, two when it is a read that ends with pi's note on the rest of the file. Short outputs use only the lines they have. Tool calls and thoughts fold together.
- The group timer spans the earliest member start through the latest finish, including model responses and overlapping tools. Sessions with incomplete timing omit the group timer.
- Failed calls fold with their peers. Each affected summary segment includes its failure count, and opening the group reveals the failed calls in order.
- A group summary reads as one sentence: `Thought for 3m 40s, searched for 1 pattern, listed 3 directories, ran 30 shell commands for 2m 05s (4 failed)`. Thinking reads as its recorded thinking time and shell commands carry their summed runtime, so time spent reasoning and time spent running can be compared at a glance. Either appears only when every member was timed; untimed thinking reads as a count (`thought 3 times`). Token count and total elapsed time stay right-aligned.
- A group summary that does not fit drops its duration, then its token count, before cutting any segment. When segments must be cut, the per-segment failure counts give way to one right-aligned total (`3 failed`), so failures are the last thing to leave the row.
- Recompute on structural events only; never per token.
- Hysteresis: two consecutive recomputes must agree before an unanimated level change. A completed fade commits its step directly.
- Visible blocks fade one step at a time, in order; a step is a level, not a block, so blocks arriving together that move a block by one level still fade it, and a block on its last standalone level folds. When a visible block is more than one level behind its target (a burst of new blocks), or a user message has ended its run, the queue is a backlog: its rows leave without fading, one row at a time, oldest block first. Within a block they go as its levels drop them, level by level, then its fold from the bottom through its heading, before the next block starts; a collapsing group lists one row fewer each time. The time between two rows spreads the whole backlog, the rows gone and those still to go, over 1.5 s, at least 25 ms and at most one fade at the current pace (`BACKLOG_TOTAL_MS`, `BACKLOG_MIN_MS` in `extensions/fade.ts`): a large backlog runs at 25 ms a row, a small one no slower than its fades would. A fade in progress when a backlog forms finishes its row, then the rest of its fold or collapse goes at the backlog's pace. New blocks arriving mid-backlog extend it. Offscreen blocks change at once, and a block the user opened is not caught up. Nothing overtakes an older block that is still on its way: a newer block waits at the level it shows until the older blocks of its run have landed, so it never joins a group ahead of them. A fade, backlog block or collapse in progress keeps the floor until it ends; a collapse that starts meanwhile waits its turn, and the oldest waiting block or collapse goes next.
- Bodies spend their budget on evidence: diffs shed unchanged context lines
  before hiding any hunk, reads keep their opening and their end, and logs and thinking previews keep their newest lines.
  An omission notice sits where lines were removed: above a tail (a log's or a thought's, streaming or settled), between the opening and the end of a read or of an opened thought cut at the cap, and below the evidence a diff or an opened command keeps. Unchanged context a diff drops from between its changes is counted below them too, and that notice reads `⋮` because the lines it counts sit between the kept rows. A notice names its side and its count, `↑ 16 more lines` when the hidden lines are above it, `↓` when they are below, `⋮` when they are between the rows around it (`^`, `v` and `:` in ASCII); a notice that stands for the whole body reads `↓`. It is italic `thinkingOff`, the faintest text grey pi's themes define, fainter than `dim`: it recedes behind the output and stays clear of the `accent` that commands and headings use, and the italic and the direction glyph set it apart from the grey output. While the pointer is over a block a click would open or close (a tool row, a thought or an open group member), its notices' words turn the `text` colour, still italic and with no background, so the hover says what the click reveals. Its header's clipped title (a shell command cut in the middle, a path cut on the left, a thought's excerpt cut in the middle) takes the same treatment: the kept text turns the `text` colour, foreground only, and the ` … ` cut mark stays as it is. A title shown whole does not change. pi's note that a read stopped before the end of its file (`[121 more lines in file. Use offset=… to continue.]`, or `[Showing lines A-B of T. …]`) is not file content: it becomes the body's last row, `↓ 121 more lines in file`, a notice like the others and counted in the same budget, so such a read keeps one line fewer at each level (two at L4, around the `⋮` notice). It gives way where it would leave the code no row of its own: a body of one row, or of two over a read longer than one line. Opening the block cannot show those lines, so this notice alone does not make a block openable.
- A preview gives each output line one row and cuts it at the terminal width; a cut line makes the row openable even when every line is present. An opened tool row wraps long lines instead. The rows that continue its command, its wrapped output and any omission notices share one cap of 400 body rows; the command takes at most half of the cap when there is output to show.
- Under an open group summary, member headers occupy consecutive rows two columns in,
  starting immediately below the summary. They read as a table: each member's label (`think`, `bash`, `read`, …) fills the width of the group's widest label, so the separator dot and the description start in the same column on every row. The widths come from every member's cells at once (`render/columns.ts`), never from measuring rendered rows. Tool and thinking bodies begin four columns past their own heading marker, two columns past the heading label. Output, omission notices, and wrapped Markdown share this inset.
- A click opens a block all the way, and the next click folds it back: a folded
  member shows its header until clicked, then its whole body. Any block with a
  truncated body (a kept tool row, a one-line thinking run) toggles the same
  way. Standalone tools stay expanded until clicked again. An opened group member stays
  expanded as turns finish and new members join the group. Every block kind behaves the same: tool rows, thoughts, group summaries and group members. A block that can open opens on a click on any of its rows, and an open block closes on a click on any of its rows; a click anywhere on a summary row opens or closes its group. Hovering a block paints its scroll bar and lights the words a click would reveal (its notices and a clipped title, above): no background highlight, no tint and no `click` chip; an open group carries no mark of its own, only the hover cell on its summary. Clicking the summary of a forming group closes it, and it stays closed as it grows; opening one of its members keeps the group open past six rows. Either click stops a collapse in progress: the group shows every member, or only its summary, at once. When merging groups disagree, any open member opens the result, else any closed member closes it.
- Column 1, the second cell of each row, is a block's scroll bar, in pi's `scrollbarThumb` and `scrollbarTrack` colours. Column 0 keeps the heading marker or indent; every block kind has a space in column 1, after its marker or inside its indent, and a row with a glyph there keeps it unpainted. Hovering a block that can open paints its preview rows, the omission notice included, as a proportional map of the whole output or thought: each cell stands for an equal share of the source lines and is filled where the preview shows none of them, so the filled cells are what a click would reveal: a log tail fills everything above its last lines and a read cut in the middle fills the middle. A preview bar of one cell (a clipped command whose body is one `(no output)` row), or one whose every cell is filled, has no position to show, so its grey would say nothing: every cell takes the hovered `accent` instead. A hovered one-row item (a group summary, a collapsed member, an inline thought, the header of a clipped command with no output) is marked on its own marker glyph, `▸`, `●` or `✻`: the glyph is drawn in the track colour on the thumb colour, and nothing else on the row changes. A block that shows everything it has gets no bar and ignores clicks. An open block in fullscreen paints the bar on its visible rows like a real scroll bar: track on every visible row and a thumb whose length is the block's share on screen (visible rows × visible rows ÷ block rows, at least one row), at the top of the track at the block's top, at the bottom at its end, and moving down as the reader scrolls down. A block that fits on screen has nothing to scroll, so its thumb fills every row, as a real scroll bar's would. While the pointer is over an open block, its bar switches to the hovered colours, `accent` thumb on `selectedBg` track: both cells change, and the thumb stays clear of the track (4.5:1 in dark, 4.4:1 in light; `accent` on `scrollbarThumb` would be 1.03:1 in dark). pi's system theme gives both scrollbar tokens one grey until the terminal reports its colours; the thumb then takes `accent` so the bar still shows a position. Inline mode cannot see the terminal's scroll position, so open blocks there have no bar.
- Thinking runs decay on the same visual ladder: the number of blocks that
  follow them in the run sets their level, so an older thought keeps a tail
  instead of collapsing to one line prematurely. A streaming preview wraps
  the reasoning into rows before it chooses the tail, so a long paragraph shows its
  newest words and arriving tokens extend the bottom row; once the run settles, the
  body renders Markdown and wraps the same way. A terminal row is
  a layout unit, not a truncation point. Streaming or settled, the omission count sits directly below the heading and the newest line stays at the bottom. The preview skips intermediate rows that never reached the screen. When it sheds previously visible rows, it drops
  one per tick. The fade applies only after streaming finishes. Hover is neutral for thinking and tool rows alike: the scroll bar in column 1 carries the
  affordance, the status glyph keeps the outcome colour.
- Opening a group shows each collapsed thinking member as one inline row, regardless of its age. Clicking a truncated thought opens its body.
- A fully visible thought has no hover bar or click action. An inline
  thought, one row, shows the start and the end of its reasoning as the reader would see it (rendered Markdown, no markup) on one line, with the cut mark in the middle when it does not fit, like a long command; one that fits whole is fully visible. A settled thought of a single line that fits its heading row uncut takes that one row at every age, since a body row would only repeat it; a streaming thought keeps its body row. Opening it
  shows the source in reading order, up to 400 body rows including any omission notice.
- Edit diffs use the file’s syntax colors for code. Added and removed lines retain their signs and use the theme’s success and error backgrounds. Their rows carry line numbers like a read's, in front of the sign: a removed line's number in the old file, an added or unchanged line's in the new, counted from the patch's hunk headers. pi's display diff, which writes the numbers after the sign, has them moved in front. An edit's file headers (`diff --git`, `index`, `---`, `+++`) and hunk headers (`@@`) take no row: the row header already names the file and the gutter numbers the lines. Between two hunks, and where pi's display diff skips unchanged lines, a `⋮` in the number column marks the jump, in the notice style, like grep's divider; it never opens or closes the body or sits beside a notice. A line's role is read from its place in the patch, counted from its hunk header, never from its prefix: a removed line reading `-- x` (shown `--- x`) is a removed line, not a file header. A shell command's diff keeps its text as it came, coloured by the same reading.
- Header token counts, rates and latency align to the right, one column short of the edge: pi draws its scroll bar over the last column while the transcript is scrolled, and a duration there would lose its unit. Spaces part the description from the metrics; the ` · ` separator stands between them only when they meet, so no dot hangs after a description. In an open group, member rows put them in columns, `out 26 @ 73/s · in 5.5k @ 2.5k/s · 1.2s`: out value, out rate, in value, in rate and duration, each right-aligned to the widest cell among the group's members, a missing cell left blank at its width. A thought's tokens are model output, so a thinking member reads `out 15 @ 3.6/s` with its in columns blank. When the rows are too narrow for the table beside a 16-column description, every member row leaves its numbers out, one decision for the whole group. Standalone rows keep the compact form. Tool headers use normal text contrast for numbers, the theme’s keyword color for `out` and type color for `in`, and muted units and separators.
- Every header writes its numbers one way: `out 26 @ 73/s · in 2.6k`, counts abbreviated past a thousand. An output rate shows only where one was measured over at least 20 tokens (`MIN_RATE_TOKENS`): a few tokens arrive in one burst, and their rate measures the burst. A thought is model output: `out 79 @ 149/s · 542ms`. A group summary totals its members: `out 3.5k · in 60k · 1m 12s`.
- Tool headers estimate the model’s output tokens for the invocation and input tokens for the returned content. Partial arguments and results update the counts.
- With throughput available, a tool header reads `out 26 @ 73/s · in 5.5k @ 2.5k/s`. Tool headers retain the duration alongside throughput. Output is model output for the tool invocation. pi-ui measures arriving argument deltas and can also use the provider’s decode timing. Input is the tool result sent back to the model. Its rate is the **whole consuming request’s prefill speed**. Results batched in one prompt share that rate.
- A live `prefill 4.2k tok/s` status appears when the provider streams processed and cached prompt-token counts and elapsed prefill time. Final server timings can supply a rate after completion. A prompt with no tool results retains its last measured prefill speed in the status line. For OpenAI-compatible streaming requests without server timing, the first generated text, reasoning or tool-argument delta freezes a client estimate, marked with `~` in tool headers (`in 1.7k @ ~4.2k/s`) and `est.` in the status line. It divides estimated new prompt text tokens since the preceding assistant message by request-to-first-output time, including transport and queueing, assuming reuse of the preceding prefix. Server timing supersedes the estimate. Recorded rates survive session reloads.
- pi-ui requests progress automatically for llama.cpp provider IDs. For a custom llama.cpp provider ID, set `PI_UI_LLAMA_TIMINGS` to that ID. Other providers’ request payloads pass through as configured.
- Group headers total the tokens of their folded members. Thinking and tool invocation arguments count as model output. Tool results count as model input. A failed call with its own row contributes only to that row.
- Write calls preview the file content as arguments arrive, follow its tail during generation, and retain the source for expansion after completion.
- A read and a single-file shell preview number their lines: each code row starts with the line's number in the file, right-aligned to the widest number the block shows, then two spaces and the code. The number is `dim`. A read counts from its `offset` (1-based, as pi counts it). A shell command counts from the first line it prints: `cat`, `head` and `bat --plain` from 1; `sed -n 'A,Bp'`, `awk 'NR>=A && NR<=B'`, `tail -n +A` and `bat -r A:B` from A. A pipe into `head`, `sed -n`, `awk` or `cat` keeps the count, so `sed -n '10,20p' FILE | sed -n '3,4p'` starts at 12. `nl` and `cat -n` print their own numbers, which move into the gutter as printed. `tail -n N`, or a pipe through `tail`, highlights its lines without numbers, since its first line is not known; any other pipe (`sort`, `grep`, …) leaves the output as it came. Blank lines take no row but keep their numbers, so a gap in the numbers shows where one was, and a read's kept opening and end show the jump across the `⋮` notice. Beside numbered rows a notice keeps the two columns: its glyph sits right-aligned in the number column and its words start in the code column. A notice between two numbered rows counts the numbers it skips, blank lines included, so it agrees with the jump in the gutter. The numbers count against the width: a preview cuts code at the columns left beside them, and an opened row wraps code under its first column with the number column left blank. When the code would get fewer than 20 columns, the whole block drops its numbers. A failed call, a read that returns a note instead of lines (an image, a first line over pi's byte limit), a shell command still running, and a shell output pi cut to its tail have no numbers counted from the start, since their first line is not known; numbers the output printed (`nl`, `cat -n`, grep) stay.
- grep output is numbered and highlighted per file. The command must start with `rg`, `grep`, `egrep`, `fgrep`, `git grep` or `ag` (after any `cd DIR &&`), and may pipe into `head`, `tail`, `sort`, `uniq`, `cat` or a `grep` filter, since those keep each line whole. The line numbers grep printed (`-n`, or `--numbers` for `ag`) move into the gutter, laid out as a read's. `ag` output is read only when its command says `--numbers` or `--nonumbers`, since whether it numbers lines without a terminal is not visible in the command. Each line's code takes the syntax colours of its file's language; adjacent lines of one file are highlighted together, so a comment that spans them reads correctly. When the lines start with their file's path, the path is removed from each line and a `dim` path row, starting at the number column, appears above the first line of each file, including the first line a preview keeps. grep's `--` between groups becomes a `⋮` in the number column, in the notice style; a `--` between two files is dropped, since the path row already separates them. grep's numbers skip the lines it did not print, so a notice beside them never counts a gap in the numbers. Numbers are read only when the command asked for them, so a log line such as `12:34:56 …` is never read as line 12, and a line whose prefix does not parse stays plain. The output stays as it came when the command uses an option that changes the prefix (`--json`, `--vimgrep`, `--column`, `--heading`, `-c`, `-l`, `-o`, `-b`, `--null`) or any option pi-ui does not recognise, or when it redirects stdout, chains commands or substitutes a command.
- File reads, single-file shell previews and grep output use pi’s filename-based syntax highlighting. Structured JSON results use its JSON grammar, and unified diffs retain semantic change colours. Ordinary logs use the tool output theme: a shell command's output is highlighted only when its command says what it printed, never by guessing from the text.
- Thinking bodies render Markdown with pi’s theme, including inline code, lists and fenced code. The detail budget applies after wrapping. Rich formatting falls back to plain text above 64 Ki UTF-16 code units to bound parser work.
- Thinking headers show elapsed time and one token count. Streaming text supplies an estimate until a provider reports reasoning usage attributable to that run. Throughput samples use text arriving after the first chunk and the interval between those arrivals. A pause leaves the last sample on screen. Newly recorded runs retain their final rates and individual durations after restore. Older messages with only response timing label it as turn time.
- Moving onto a blank separator clears the hover bar immediately. Clicking the separator leaves the adjacent blocks in their current state.
- Tool, thinking, and group durations show milliseconds below one second and seconds thereafter.
- A running bash header shows elapsed execution time and refreshes every 100 ms, even while the command is silent. Long commands shorten to leave room for the timer. On completion the header uses pi’s recorded duration.
- An opened block never cuts its title, whatever the tool: a shell command, a path (read, edit, write, ls, find), a grep pattern, a web query or URL, an MCP argument. The header carries the title's first segment instead of the cut, and the rest, every following line of a command included, continues on the rows below in the column where the title starts, above the output. A command wraps at spaces; a path breaks after a `/` where one fits, so each row but the last ends with a directory. When there is output to show, these rows take at most half of the opened block's cap, and a notice counts the rest. A closed block keeps the cut (in the middle for a command, on the left for a path), and a header that cuts its title makes the block openable even when its body shows everything, a silent command's included. While the pointer is over an opened block, the title's rows take the lit `text` colour like a clipped title's.
- A shell command that creates, changes or deletes files in its git work tree shows each file after its output, as Claude Code does: a `dim` path row starting at the number column (relative to the session's directory), then the file's diff read like an edit's (line-number gutter, the success and error backgrounds, no file or hunk headers, `⋮` between hunks, the file's syntax colours). A new file reads as all additions; a deleted file, a binary file and a file past the snapshot's limits show a note in the notice style (`deleted`, `binary file changed`, `too large to diff`) instead of lines, and a file rewritten with the same bytes is not shown. These rows are body rows: they share the level's budget with the output, the files take the larger half when both cannot fit (the output keeps at least one row), the files drop unchanged lines before changed ones and count what they hide in one notice, and a block whose file rows do not all show opens to show them. Only top-level shell calls in a git work tree are watched; files ignored by git are not. A file is read only when its directory resolves inside the work tree. A tracked file git checks out with CRLF line ends (`core.autocrlf`, `core.eol`, the `text`/`eol`/`crlf` attributes) is diffed against its stored content converted the same way; other checkout filters (Git LFS, `ident`) are not applied. pi runs a message's tool calls in parallel, so a file an `edit` or `write` call names is left out when that call was in flight as the command started or started while it ran. The changes are recorded on the tool result (`details.piUiChanges`), so a reloaded session shows them. Group summaries do not count changed files.
- A one-row shell preview uses the latest substantive line when trailing output
  consists of single characters or closing delimiters. A single-value result stays visible.
- A failed shell puts the exit status in its header and stderr in the body:
  the outcome stays scannable while the evidence stays readable.
- Long shell commands truncate in the middle, keeping the opening verb and the
  end target; paths keep their basename instead.
- A user message keeps its own rows only, on the neutral `toolPendingBg` instead of `userMessageBg`: no padding row above or below it (`extensions/user-message.ts`).

## Width and glyphs

- Measure with `visibleWidth`/`truncateToWidth`; never `String.length`.
- Every line must fit the supplied width exactly; no overflow, no ANSI bleed across lines.
- Every cut shows the cut mark ` … `: an ellipsis with a space each side, bold in the theme's `text` colour (`cutMark` in `render/kit.ts`). It marks a command cut in the middle, a path cut on the left, a line cut at the width and an excerpt's omitted opening alike, and the width math counts its three columns. The text on either side of a cut is styled on its own, so the mark's weight never leaks into it.
- Glyph sets: `nerd`, `unicode`, `ascii`. A card must render in all three; ASCII is the accessibility floor.
- Motion: spinner frames and pulse cadence are data. Registry states carry them as frames; `ds:show` prints the last frame and the fixtures record the first.

## Definitions

- **Run**: everything between user messages.
- **Turn**: one model response plus the tool calls it made.
- **Block**: a rendered transcript unit (assistant text, thinking run, tool row, group summary, notice).
- **Group**: contiguous collapsed tool rows of one class, summarised on one line.
